Fix the seeded bugs

Each task copies the repository, introduces one real bug, and hands the agent the failing test and a ticket. A patch is only accepted if the target test passes, nothing that passed before now fails, no test file was touched, and something in the source actually changed.

Offline replays prepared replies. It exercises the sandbox, the edit applier, the test runner and the verifier – but not the model's reasoning. Only the live column says anything about the agent.

The eight bugs

Every one of these is a mistake that has been shipped by somebody. The fix is not stored anywhere – the benchmark says only how to break the code and which test should then fail, so the agent is graded on whether the suite goes green, never on whether it wrote the lines a person would have.

The check that matters

An agent that cannot work out why total_with_tax(100) == 120 fails has an obvious alternative: change the 120. The suite goes green, the exit code is zero, and every metric built on “did the tests pass” reports success. Ask the model what it did and it will say it corrected the expected value – a true description of the edit and a false description of the work.

So the test files are hashed before the agent starts and again at the end. If any hash moved, the patch is rejected however green the run was. The rule is enforced twice on purpose: layer 6 refuses the edit at the door, and layer 8 checks the room afterwards and does not care how anything got in.

What stops the loop

Two facts, neither of which is persuadable: the exit code of the test run, and arithmetic on the budget. Not the agent's opinion about whether it is finished. An agent asked “are you done?” will eventually say yes whether or not it is.

What this sandbox is, honestly

A blast-radius limiter, not a security boundary. It stops the agent editing files outside its working copy, and it stops a bad patch damaging the original repository. It does not contain code the agent causes to run – the test suite executes as an ordinary subprocess with the same permissions this process has. Genuinely untrusted code needs a container. Saying “sandbox” and meaning “I checked the paths” is how people end up believing they have a boundary they do not have.
